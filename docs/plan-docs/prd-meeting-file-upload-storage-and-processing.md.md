# Plan: Загрузка файла встречи, хранение и обработка

**PRD:** @docs/prd-meeting-file-upload-storage-and-processing.md
**Дата:** 13 августа 2026

## Фазы реализации

### Фаза 1: backend-file-upload-storage

**Цель:** Tracer Bullet — владелец встречи может загрузить файл, файл сохраняется в объектном хранилище с записью в БД, отображается в списке, скачивается и удаляется; работают проверки принадлежности и лимитов.
**Затрагивает:** backend / database / infrastructure
**Задачи:**

- [ ] Добавить контейнер Minio (S3-совместимое) в docker-compose и конфигурацию доступа к S3 (переменные окружения + модуль/провайдер хранилища в API).
- [ ] Добавить Prisma-модель `MeetingFile` (name, mimeType, size, status, objectKey, meetingId, userId) с миграцией; связь с `Meeting`.
- [ ] Добавить endpoint загрузки `POST /meetings/:id/files` (multipart, защищён JWT): проверка принадлежности, 403/404 для несуществующей или чужой встречи, отклонение файлов больше 50 МБ и неразрешённых форматов с понятной ошибкой, сохранение в Minio + запись в БД со статусом «processing».
- [ ] Добавить endpoint списка `GET /meetings/:id/files` (только владелец), возвращающий имя, тип, размер, дату загрузки и статус, плюс endpoint скачивания по ссылке.
- [ ] Добавить endpoint удаления `DELETE /meetings/:id/files/:fileId` (только владелец): удаление объекта из Minio и записи из БД.
      **Когда готова:** владелец может загружать, просматривать список, скачивать и удалять файлы; чужие и несуществующие встречи возвращают 403/404 и ничего не создают; файлы больше 50 МБ или неразрешённого формата отклоняются с понятным сообщением; сразу после загрузки файл появляется в списке со статусом «processing».

### Фаза 2: background-processing-pipeline

**Цель:** Файлы обрабатываются асинхронно в фоне с отслеживаемым статусом (processing -> ready | failed); для аудио/видео создаются транскрипт и превью, для документов — превью, извлекаются доступные метаданные.
**Затрагивает:** backend / infrastructure
**Задачи:**

- [ ] Добавить сервисы Redis + worker в docker-compose и фоновый процесс воркера в API; ставить задачу в очередь сразу после загрузки.
- [ ] Задача извлечения метаданных для всех файлов (формат, размер, длительность/кодек для медиа, количество страниц для документов и т.д.).
- [ ] Генерация превью/миниатюр для документов (pdf/txt/office) и медиа (аудио/видео).
- [ ] Транскрипция аудио/видео (создание и хранение транскрипта; его отображение в UI — вне скоупа).
- [ ] Переходы статуса: processing -> ready при успехе, processing -> failed при сбое; файлы со сбоем остаются в списке.
      **Когда готова:** после загрузки файл автоматически переходит processing -> ready; аудио/видео имеют транскрипт и превью, документы — превью, извлечены доступные метаданные; при сбое статус меняется на «failed», файл остаётся в списке.

### Фаза 3: frontend-meeting-detail-page

**Цель:** Страница деталей встречи доступна по прямой ссылке и показывает список файлов (имя, тип, размер, дата, статус), загруженный с защищённого JWT-эндпоинта через прокси веб-приложения, с формой загрузки и действиями удаления/скачивания.
**Затрагивает:** frontend
**Задачи:**

- [ ] Страница деталей встречи `/meetings/[id]` с клиентской авторизацией, загружающая файлы из `GET /api/meetings/:id/files` через прокси `/api/*`.
- [ ] Рендер списка файлов: имя, тип, размер, дата загрузки и статус обработки.
- [ ] Форма загрузки (multipart POST через прокси) с клиентской валидацией лимита 50 МБ и форматов, зеркалящей правила бэкенда.
- [ ] Действие удаления и ссылка скачивания для каждого файла.
- [ ] Обработка ошибок 403/404 (чужой или несуществующей встречи) и ошибок загрузки.
      **Когда готова:** страница открывается по прямой ссылке, список файлов подгружается с JWT-эндпоинта, загрузка/удаление/скачивание работают сквозным образом, не владельцы видят ошибку доступа.
