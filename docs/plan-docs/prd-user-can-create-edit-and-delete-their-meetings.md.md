# Plan: Пользователь может создавать, редактировать и удалять свои встречи

**PRD:** docs/prd-user-can-create-edit-and-delete-their-meetings.md
**Дата:** 16 августа 2026

## Фазы реализации

### Фаза 1: backend-meeting-crud

**Цель:** Tracer Bullet — полный CRUD встреч на бэкенде: владелец создаёт, просматривает список и детали, редактирует и удаляет встречу (название, описание, время, участники) с валидацией; удаление встречи с файлами блокируется; чужие встречи недоступны. (Создание и чтение уже реализованы — фаза добавляет недостающее.)
**Затрагивает:** backend / database
**Задачи:**

- [ ] Добавить поле `description` в Prisma-модель `Meeting` с миграцией; добавить его в `CreateMeetingDto` и обработчик создания.
- [ ] Добавить `UpdateMeetingDto` (название, описание, время, участники — все атрибуты изменяемы) и PATCH-эндпоинт `PATCH /meetings/:id` с обновлением только своей встречи.
- [ ] Добавить DELETE-эндпоинт `DELETE /meetings/:id`: только владелец; при наличии файлов у встречи (`MeetingFile`) — понятное сообщение об ошибке, встреча и файлы остаются на месте; для чужой/несуществующей — 403/404.
- [ ] Валидация: обязательные название и время, описание опционально, каждый участник — корректный email; невалидные данные отклоняются на уровне DTO.
- [ ] Тесты: unit-тесты хендлеров update/delete (принадлежность, блокировка при файлах, валидация) и e2e-тесты полного цикла create → update → delete + доступ чужого пользователя (403/404).
      **Когда готова:** владелец создаёт, видит, редактирует и удаляет встречу; чужая/несуществующая встреча возвращает 403/404 и ничего не меняет; встреча с файлами не удаляется с понятным сообщением; невалидные данные (пустое название, нет времени, плохой email) отклоняются; все эндпоинты под JWT.

### Фаза 2: backend-email-invitations

**Цель:** Участникам встречи отправляется email-приглашение при создании и при изменении встречи, что автоматизирует созыв без ручной коммуникации.
**Затрагивает:** backend / infrastructure
**Задачи:**

- [ ] Добавить сервис отправки писем (SMTP) с конфигурацией через переменные окружения.
- [ ] Отправка приглашения каждому участнику при создании встречи (название, время, состав).
- [ ] Отправка актуального приглашения при редактировании встречи (изменение атрибутов и/или состава участников).
- [ ] Тесты: mock SMTP-транспорта — при создании письмо уходит каждому участнику; при изменении состава/атрибутов участники получают актуальное приглашение.
      **Когда готова:** при создании встречи все участники получают email-приглашение; при редактировании атрибутов или состава — актуальное приглашение; отправка покрыта тестами с моком транспорта.

### Фаза 3: frontend-meeting-management

**Цель:** Пользователь управляет встречами через веб-интерфейс: видит список своих встреч, создаёт и редактирует встречу (название, описание, время, участники), удаляет встречу с подтверждением и понятной ошибкой, если удаление заблокировано.
**Затрагивает:** frontend
**Задачи:**

- [ ] Страница списка встреч `/meetings`, загружающая данные из `GET /api/meetings` через прокси, с переходом на детали встречи.
- [ ] Форма создания встречи (название, описание, время, участники) с клиентской валидацией (обязательные поля, формат email) и POST через прокси.
- [ ] Редактирование встречи: форма, предзаполненная данными встречи, с PATCH через прокси.
- [ ] Удаление встречи с подтверждением; отображение ошибки при удалении встречи с файлами.
- [ ] Тесты (vitest + Testing Library): рендер форм, валидация, вызовы API, обработка ошибок.
      **Когда готова:** со страницы `/meetings` пользователь видит свои встречи, создаёт новую, редактирует атрибуты и удаляет встречу; встречу с файлами удалить нельзя и показана понятная ошибка; `npm test -w @mpixel/web` зелёный.
